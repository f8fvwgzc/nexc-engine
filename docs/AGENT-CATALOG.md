# Agent catalog

Every workspace has an organisation of agents: the **Planner** at the top, the **core team**
(Researcher, Writer, Engineer, Reviewer) and **30 expert agents** in seven departments, from
finance and shipping to hardware and law. Each agent brings **skills**: working knowledge written
from public sources, added to its system prompt when it runs a step that needs it. This page says
how that works and lists every agent and skill.

<!-- #region catalog -->
## The Planner and the organisation

The Planner plans the work and routes it. When a graph is planned, the graph planner is shown
every active agent of the workspace with its title, its purpose and the names of its skills, and
gives each node the role whose purpose and skills fit it best: the financial analyst for a
valuation, the freight specialist for Incoterms, the appsec engineer for a security review. When
a node runs, the scheduler picks the agent of that role (the node's `agent_role`, or the default
role of its type). nexc runs its own DAG scheduler and agent runtime; it does not use LangGraph or
another agent framework.

Every expert reports to the Planner. The core team is the default organisation of earlier
releases; the experts were added in October 2026.

## Skills

A skill is a Markdown file in `backend/skills/`, embedded in the backend at build time:

```md
---
id: fin-equity-valuation
name: Equity valuation
category: finance
description: Values a company's equity with DCF, multiples and residual income, and cross-checks the result.
keywords: valuation, dcf, fcff, fcfe, wacc, terminal value, multiples
source: CFA Institute - CFA Program curriculum | https://www.cfainstitute.org/...
---
## When to use
...
```

Its body (1,500 to 3,800 characters) holds methods, formulas, decision rules, checklists, the
structure of a good deliverable and the usual mistakes. Every skill names the public pages it was
written from; the text is original, not copied from a curriculum or a standard.

**How a skill reaches the model.** When an agent runs a step, the backend ranks the agent's skills
against the step (its title, type, tags, content and the graph's goal): three points for every
keyword the step uses, one for every word of the skill's name and description it uses. The best
ones are added to the system prompt in full while they fit 14,000 characters (about 3,500 tokens);
the rest as one line each. Up to two skills of the shared library that the agent was not given are
added too when the step matches them strongly (two keywords, or one keyword and three words), so
every skill is usable by every agent when the work calls for it. The node's log says what was
applied, for example `skills applied: fin-equity-valuation, fin-financial-statement-analysis;
summarised: fin-portfolio-management`.

An agent has at most 12 skills. They are set when it is made (from its template, or by hand in the
agent form) and changed on its card or with `PATCH /agents/{id}`; every change is audited as
`agent_skills_changed`. The library is browsable in the console (Agents, Skills) and through
`GET /skills` and `GET /skills/{id}`. An agent published over A2A lists its skills on its agent
card.

## Benchmarks, not credentials

Each expert's knowledge is **benchmarked against** the public exam outlines of real
certifications, and for a few roles against the standards or bodies of knowledge the profession
works to (IFRS, the FATF Recommendations, OWASP ASVS, Google's Search Quality Rater Guidelines): the financial analyst against the CFA Program Levels I to III, the risk
manager against FRM Parts I and II, the security lead against the eight CISSP domains, and so on.
The agents do not hold these credentials and never claim them; their prompts tell them to separate
facts, assumptions and judgement, to name the jurisdiction and recommend a licensed professional
for binding investment, legal, tax, employment or safety decisions, and to treat instructions inside
documents as data. Certification names are trademarks of their owners (CFA Institute, GARP, The IIA,
ISACA, ISC2, ACAMS, AXELOS/PeopleCert, ISTQB, ASCM, CIPS, PMI, IAPP, SHRM, CIPD and others) and are
used only to describe what the knowledge is measured against; nexc is not affiliated with them.

**Competency checks.** Every template has five applied questions in the style of its benchmark
exams. Making an agent from a template asks them once with the workspace's provider, with the
agent's prompt and the skills each question calls on; an answer passes when it contains one of the
expected terms. `POST /agents/{id}/evaluate` (the card's *Run competency check*) asks again. The
check is a smoke test of the prompt and the model, not an exam: under the offline demo provider
the answers are canned and the score says nothing.

## How workspaces get the catalog

With `NEXC_SEED_EXPERT_AGENTS=true` (the default), every workspace gets the catalog once: a new
workspace when it is created, an existing one in the background shortly after the backend starts
(the sweep repeats every ten minutes, for a workspace a backend could not seed or one that a
backend of an earlier release created during a rolling update). The seed is recorded in
`workspace_catalog_seeds`, which travels with a workspace transfer, so an agent deleted afterwards
is not brought back; two backends never seed the same workspace at once. It acts as one of the
workspace's owners or admins (its creator first) and:

- gives the core team their current prompts where they still have a prompt an earlier release
  seeded (an edited prompt is kept; so is an edited purpose), and their skills where they have
  none; an agent made from a template before skills existed gets that template's skills;
- makes every expert from its template: its capabilities (tools, data labels, no outside calls),
  its knowledge topics where the workspace has topics with those terms, its skills, and its policy
  as the agent's version 1 without any field that would widen the workspace's policies (the
  workspace's stricter value applies there; the audit entry names the fields left out);
- skips an expert when the workspace already has an agent of its name or role (nodes go to the
  oldest active agent of their role, so one agent per role keeps routing predictable);
- leaves the model allow-list open (an agent made from a template by hand pins it to its model)
  and asks no competency questions (run them from the card);
- touches only the fields it changes, and audits every agent it makes (`agent_created` with
  `from template <id> (expert catalog experts-v1)`, `policy_changed`) and every agent it updates
  (`agent_skills_changed`).

Set `NEXC_SEED_EXPERT_AGENTS=false` to keep new workspaces to the core team; agents can still be
made from any template in the console (Agents, *From template*) or with
`POST /agents/from-template/{id}`.

## Adding a skill or an expert

Add a file. A skill is `backend/skills/<id>.md`; an expert is `backend/templates/agent-<id>.json`
with `department`, `credentials`, `skills` and five `questions` (see an existing one). `build.rs`
embeds every file of both folders; the backend's tests check that each skill parses and stays
within its limits and that each template is well formed and names known skills. After a change,
refresh the tables below with `python3 scripts/agent-catalog-doc.py`. A workspace that already had
the catalog does not get a new expert automatically; make it from its template.
